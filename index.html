Keyword Lines, Not Data Flow

codeintel-data-flow-analyzer lists every line in a Python source file that mentions a sensitive keyword, and runs bandit on the file. Matches are unfiltered substring hits, comments included. The tool does not trace data flow and does not identify leaks or injection points.

Matched Lines Are Written in Full

Matched lines go into the local report in full, under the report section named keyword_lines. A real secret sitting on a matched line will therefore appear in the report file in full.

Keywords match as plain substrings, case included. A keyword inside a comment counts. A keyword inside a longer name counts. The same word with a different capital does not count. A line naming two keywords still gets listed once.

Usage, the Placeholder and the Parser Line

./codeintel-data-flow-analyzer [params]

That is the README usage line, shown flagged as a placeholder. Alongside it, what the argument parser in main.py genuinely accepts:

python3 main.py --source_file FILE --sensitive_data KEYWORDS

Both --source_file and --sensitive_data are required. Omit either one and the run is refused as a usage error. The README line is not rewritten to look correct. The gap between the two lines is the point.

The Seven Log Entries

-hShow help message and exit.
--source_filePath to the Python source file to analyze. Required, from the parser.
--sensitive_dataNo description provided. Beneath, from the parser: a comma separated list of sensitive data keywords to track, for example password, api_key. Required.
--output_fileOptional file to write the analysis results to.
--log_fileOptional file to save logs to.
--bandit_severity_thresholdNo description provided. Beneath, from the parser: the threshold severity for bandit findings, one of LOW, MEDIUM, or HIGH, default MEDIUM.
--bandit_confidence_thresholdNo description provided. Beneath, from the parser: the threshold confidence for bandit findings, one of LOW, MEDIUM, or HIGH, default MEDIUM.

Bandit Findings and Bandit Status

When Bandit Fails the Run Fails

If bandit is missing, the run exits 1. If bandit output cannot be parsed, the run also exits 1. The JSON report records a bandit_status field naming the failure. The report is printed or saved before that exit, so a failed bandit run still leaves its keyword lines behind, and its bandit status too. A source file that does not exist is refused before any scanning, with an error and exit 1. Nowhere on this page is a completed run described as a leak found or a flow traced. The tool lists lines. The tool runs bandit. That is the whole of its work.
